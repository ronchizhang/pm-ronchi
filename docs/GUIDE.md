# 产品Ronchi v2.0

> 一句话：**它不给你一份更好的 PRD，它把「你没想到的那一问」指出来。**

> 代号：`pm-ronchi`｜版本：**v2.0**｜建立：2026-11-01｜最近更新：2026-11-06
> 仓库：`github.com/ronchizhang/pm-ronchi`｜装法见 [README](../README.md)

## 一、它能干什么

| 能力 | 你说什么 | 它给什么 |
|---|---|---|
| **需求评审** | "帮我看看这个需求值不值得做" | 结论（做/不做/改完再评/待验证）+ 缺的那一问 + 依据 + 追问 |
| **PRD 评审** | "评审一下这份 PRD" | 五问缺位表 + 覆盖缺口清单（异常流/权限/空态/并发/边界值） |
| **方案找漏洞** | "这个方案有什么问题" | 备选方案是否评过 + 边界推演 + 成本账 |
| **技术评审陪跑** | "技术给了这版表结构，帮我看" | 表名 → 与 ER 图比对 → 该问的三个"为什么这么设计" |
| **方法论问答** | "业务抽象什么时候该做" | 判据 + 原话出处（区分 `【原话】` / `【引申】`） |
| **算账** | "这个需求要 5 人日" | 5000 元 → "如果你是老板，愿意花吗" |
| **评人（教练态）** | "看下这段评审记录，他哪里没想清楚" | 姿态判断 + 分诊（没想清楚/知识盲区/图省事）+ 差距清单 |
| **带人反馈** | "新人这份方案怎么给他反馈" | 只报差距，不给改法（这是刻意的） |
| **接住崩掉的人** | "他文档写完要重做，整个人崩了" | 先给一个 30 分钟内能做完的动作，再谈方法 |
| **交互评审** | "这份 PRD 的交互有没有问题" | 图文对账 + 列表页/详情页/组件逐项卡 + 按"会不会出错"排序 |
| **带原型的评审** | "这是 HTML 原型，帮我看这版" | 定位页面 → 图与说明文字配对 → 交互缺陷四段报法 |
| **自动取材** | "这份 docx 你看下交互" | 跑 `extract_prd.py` 拆出文字+图+图文配对，不用每次重写提取代码 |

**它不干的事**，看到别硬求：写 PRD 全文、画交互稿、算精细 ROI、替你决定优先级、给真实用户数据。

> 交互评审有个硬前提：**没有图、没有能打开的页面，它只评"有没有写"，不评"对不对"**，而且会明说这个缺口——不会硬猜。

## 二、两个平行入口

| | 工具态（评物） | 教练态（评人） |
|---|---|---|
| 输入 | 一份需求、PRD、方案、表结构 | 一段会议纪要、某个人的方案 + 他的应对 |
| 问的是 | 这个方案成不成立 | 这个人想清楚了没有 |
| 产出 | 结论 + 依据 + 追问 + **分发清单** | 姿态 + 韧性 + 分诊 + 差距清单 + **一个能马上动的动作** |
| 共同底线 | 判方案，不判人 | 只报差距，不给成品 |

**入口自动判断**：贴的是"东西"→ 工具态；贴的是"过程"→ 教练态。判错了说一句"这次评人"就切。

两者结构上平级，但**本心优先于方法**：先看他是求真还是自保，再看方法用没用对。

## 三、它会问你的五个问题（内核）

任何需求进来，它都走这一串：

> **谁 → 在什么场景下 → 遇到了什么问题 → 提供了哪些解决方案 → 为什么这是当前最优**

前四问摆事实，第五问才是主战场。**它卡人的位置永远在第 4 问**——大部分 PRD 的病都是"只有一个方案，然后论证它最好"。

同一个结构它用在四处：评需求、找对标（按场景不按行业）、评人、写文档。

## 四、八个最佳应用案例

### 案例 1｜砍流程类需求：它会把风险账翻出来

**你说**：销售嫌合同审批太慢，想砍掉法务那一步，看着是纯效率问题。

**它怎么做**：
1. 先拆每个节点在防什么 —— 运营防填错、财务防账号错、法务防合同风险
2. 指出这不是"流程繁琐"，是**局部效率 vs 全局风险**
3. 给结论时不说"不能砍"，而是问：**"删掉之后这个风险由谁承担？"**
4. 判定受益范围 = 一个人（销售 A）→ 拉 B/C/D 的样本，否则算闭门造车

**关键**：它把"简化"翻译成"风险转移"，让需求方自己回答谁来兜。

---

### 案例 2｜顺手人情类需求：1 人日是一道分界线

**你说**：小王要个批量导出，大概 3 人日，就他一个人用。

**它怎么做**：
- 3 人日 > 1 人日 → 不适用"顺手人情"，进入算账
- 3 × 1000 = 3000 元 → **"如果你是老板，愿意花 3000 块解决小王一个人的效率问题吗？"**
- 愿意 → 做；不愿意 → 先找替代方案（手工、脚本、买工具、招人）
- 如果他说"其实 1 人日就能搞定" → 直接放行，**不做价值判断**

**关键**：它不羞辱小需求，但也不让"每个都很小"变成什么都做。额度就是 1 人日。

---

### 案例 3｜只有一个方案的 PRD：它停在第 4 问，不往下评

**你说**：这是我写的 PRD，帮我看看有没有问题。

**它怎么做**：
- 出五问表：谁 ✅ / 场景 ✅ / 问题 ⚠️ / **有哪些方案 ❌** / 为什么最优 ❌
- 写一句：**卡在第 4 问。**
- 然后停下，只给追问：「除了这个方案，还评过哪几个？为什么排除？」「如果只能做一半，砍哪一半？」
- **不评方案好坏**——因为方案的好坏取决于它回答的是哪个问题

**关键**：它拒绝在你缺备选时给评价。这是设计，不是偷懒。

---

### 案例 4｜业务抽象：判断"该不该合并"

**你说**：我们已经有资金账户了，把积分、预授权额度、信用额度也做成账户吧，长得一样。

**它怎么做**：
- 拿水系判据卡一下：**它们之间会发生流转吗？**
- 积分/额度/信用是三个独立仓库，没有一条水流穿过 → **不能合并**
- 反过来，客户项目账户、供应商账户、人员币种账户之间钱在流动 → 是一套
- 币种不是另一个仓库，是同一条水系的分河道（跨河道要结汇）
- 最后推边界：推不出边界的抽象算失败；能说清"水流到哪为止"才算成立

**关键**：**抽象层次不是越高越好。** 抽到"能覆盖一切"那层，会得到一个装得下一切但装不准的模型。

---

### 案例 5｜评人：先判姿态，再分诊

**你说**：（贴一段评审会记录）看看这个人哪里有问题。

**它怎么做**：
1. **姿态门**：他是在找答案，还是在找支持？（反复解释同一方案、把黑白讲反 → 找支持）
2. **分诊**：没想清楚（态度）/ 知识盲区（能力）/ 图省事（实现层理由）——三者处理完全不同
3. **差距清单**：只列他漏了什么，**不写怎么补**
4. 看到"没人反对"会当警报：**大家不跟你争的那一刻，纠偏通道就关了**

**关键**：给知识盲区的人紧节奏，他会更慌；给没想清楚的人做科普，他会觉得你在绕开问题。所以顺序不能反。

---

### 案例 6｜0 到 1 与 AI 功能：两条拦截

**你说**：我想做一个新产品，帮客户管供应商。

**它先拦**：**"这件事用微信群 / 人工能不能先跑通？"** —— 产品是固化手段，不是验证手段。业务没跑通就先做产品，等于把没想清楚的东西用代码焊死。

**你说**：我们想加个大模型功能，其实解决不了什么问题，但能对外讲。

**它怎么答**：你的两条判据都认——① 真能解决问题且成本低；② 成本无所谓，但能拿政府资源、能让资方青睐。但它会补一句时效：**叙事收益只在技术更替的窗口期成立**，窗口一关，这条只剩成本。并建议先过①再看②。

---

### 案例 7｜交互评审：只认"用户会怎么错"，不认"我觉得不好看"

**你说**：这是客户列表页的原型（贴了张图），帮我看下有没有问题。

**它怎么做**：

1. **先对账，不先评**：图上有搜索框，但文字没说搜哪些字段；文字写"支持批量操作"，图上没有批量入口 → **先出对账清单，不进规范评审**
2. **列表页查两件事**：
   - 易搜索：搜的是名称还是编号？模糊还是精确？搜不到时页面说什么？
   - 易定位：12 列平铺、无筛选无排序；**翻到第 4 页点进详情再返回，回到第 1 页还是第 4 页？**——这条几乎每份 PRD 都漏
3. **报法带后果**：
   > "销售要找上周签的那家，只能一页页翻；一天做 5 次，每次多花 2 分钟。"
4. **组件顺手指一下**：状态用开关没问题（拨了即生效）；但表单里的"是否开票"也用开关就是错的——拨完以为保存了，其实没提交。

**关键**：它不给"改成左右布局"这类成品，只给规范和后果。**改法让产品经理自己出。**

---

### 案例 8｜人崩了：先给动作，再谈方法

**你说**：团队里有个小伙伴，文档好不容易写完，一评审发现方向不对得推倒重来，人当场就崩了，后面拖着不想改。说他又怕他想多。

**它怎么做**：

1. **先过姿态门，再看韧性门** —— 他不是在找答案，也不是在找支持，是**扛不住**。这个状态下任何方法论都会被听成宣判。
2. **拆病灶**：痛的不是方案，是**沉没成本**。他把"我的方案错了"读成了"我这个人不行"——皮实就是能把这两件事分开。
3. **给动作，不给道理**：
   > "现在能动的下一步是什么？先做那一步。" 把推倒重来拆成三件，今天先交第一件。
4. **明说不要说的话**："这没什么大不了的""你已经很棒了""你要皮实一点"—— 最后这句尤其不能出口，听到的是"你不行"。
5. **给管理者一个判断标准**（不是给那个人的标签）：
   > "接受不了批评、接受不了错，在这个迭代速度下会拖死整个组。但先确认两件事：你的批评站得住吗？是不是反复推翻又不给理由？如果是后者，那是判断机制的问题，不是他逆商不够。"

**关键**：它把"态度问题"翻译成"沉没成本没被处理"。**恢复靠动作，不靠安慰**——这跟他"10 秒盘出框架"是同一个逻辑：用速度打断情绪。

## 五、其他场景一句话怎么用

| 场景 | 一句话说法 |
|---|---|
| 老板拍了个你不理解的需求 | "老板要这个，我不理解，帮我理一下该问什么" |
| 两个部门抢同一批研发 | "两个部门都要，我该让谁先排"（它会告诉你这不一定是你的活） |
| 上线了没效果 | "上个功能没达标，怎么处理"（它会让你回池，并逼你写一行"当初哪判断错了"） |
| 文档怎么写 | "这个交互我讲不清，文档该怎么写"（会给载体升级链，甚至给你一个能点的 JS） |
| 对标 | "做聊天功能，该看哪些产品"（按场景检索，不限行业） |
| 上线炸了归谁 | "这个线上问题该谁背"（判据是用例里有没有，不是谁能力差） |
| 怎么带新人 | "他方案总是不行，我该怎么跟他说"（只报差距，不给改法） |
| 详情页信息太乱 | "这个详情页要放什么"（先列"用户想知道"和"我们想让他知道"两个清单，差集就是战场） |
| 组件选型拿不准 | "这里用下拉还是单选"（按选项数、用户知不知道要选什么、是否即时生效三条判） |
| 下属被推翻就崩 | "他文档要重做就不想改了，怎么说"（先给动作，不给道理） |

## 六、输出长什么样

**工具态五段**（一屏内）：结论 → 缺的那一问 → 依据（受益范围/成本账/边界/验证）→ 该问的问题 → **分发清单**（对象/说什么/目的/渠道）

**教练态四段**：姿态判断 → 分诊 → 差距清单 → 下一步

**例外**：人已经崩了（解释当初、反复提沉没成本、"再想想"泡着）→ 四段全让位，先给一个 30 分钟内能做完的动作。

**正式报告**：说"出报告"，它按 `assets/review-report-template.md` 出，含"哪些属于引申、哪些本人没给判据"的备注。

## 七、用它用得好的五个习惯

1. **一次只放一件事。** 丢一堆需求进去，它只能给你一堆模糊判断。
2. **它不给你改法时不要催。** 那是刻意的——给了改法，对方就是在照着你的思维改。
3. **想往深挖就说"继续追问"。** 它会往下再问三层，直到问出事实。
4. **要评人就明说"这次评人"。** 它默认评物。
5. **它说"这块没给判据"时，那是实话。** 比如未达标复盘的流程、平台型两侧冲突的定量判定——目前是空白，它不会编。

---

## 八、什么时候别用它

- 要精细 ROI / 财务模型 → 它只做粗算，做细就没人用了
- 要真实用户行为数据 → 它看不到，只能看"长成什么样"
- 要 UI 稿 / 视觉方案 → 不在能力范围（你能判断好坏，只是不用工具）
- 要它替你定优先级 → 排序权不在产品经理手上时，它的建议是"别争这个，把信息摆清楚"
- 平台型两侧冲突偏谁 → 只给方向（偏袒稀缺侧、动态平衡），给不了定量结论
- 想拿"皮实"当尺子压人 → 它会先反问你的批评站不站得住（这是刻意的护栏，不是它不懂你的意思）

## 九、文件结构与怎么扩展

```
pm-ronchi/                             ← 产品Ronchi v1.9
├── SKILL.md                          入口：双态路由、五问主链、15 条硬规则、8 条禁止行为
├── README.md                         仓库门面（开源用）
├── docs/
│   ├── GUIDE.md                      本文件（完整使用手册）
│   ├── index.html                    落地页
│   ├── demo-review.html              示例评审报告（虚构需求）
│   └── structure.svg                 五问主链与双入口结构图
├── references/
│   ├── core-principles.md            判据全集，15 节，每条标【原话】/【引申】（含四条底色与皮实）
│   ├── review-playbook.md            工具态十步 + 检查项 + 追问句式
│   ├── interaction-review.md         交互评审：取材 → 对账 → 列表页/详情页/组件 → 报法
│   ├── writing-spec.md               产出侧：线框四级 + 三层规则归属( BR/IR/FR ) + 字段表 + 标号法（CRM 示例）
│   ├── impact-translation.md         12 维度影响翻译表（PM 语义 → 底层影响 → 必写 vs 不写）
│   ├── coach-playbook.md             教练态三道门：姿态 → 韧性 → 分诊
│   └── voice.md                      措辞红线：判方案不判人；扛不住的人怎么接
├── scripts/
│   └── extract_prd.py                取材脚本：docx/html/md/xlsx → 文字+图+图文配对（纯标准库）
└── assets/
    └── review-report-template.md     评审报告模板
```

**补三样东西，它就从"像你的方法"变成"像你"：**

1. **你评审时的原话**（措辞决定像不像，判据可以推导，措辞不能）→ 追加进 `voice.md`
2. **一个搞砸的案例**（让它知道在哪个位置该刹车）→ 追加进 `core-principles.md` 末尾
3. **一份脱敏 PRD 真件**（合格基线）→ 放 `assets/`，在 `review-playbook.md` 里引用

改完之后不用重启，下次对话自动生效。
