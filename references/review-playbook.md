# 工具态：需求与 PRD 评审

评的是**物**。目标不是给一份更好的方案，是让缺失的那一问露出来，然后让对方自己去补。

> 说明：本文件中的检查项，除标注【原话】外，均由他的判据推导而来（`【引申】`），不是他逐条口述过的清单。使用时不要冒充成他的原话。

## 十步流程

> 第 1–7 步评**该不该做**，第 8 步评**做出来好不好用**。两关不能混：业务不成立的方案，交互评得再细也没意义。

### 第 0 步：分流
先判四件事，判完才知道该用哪套判据：

1. **终端类型**：C 端 / B 端 / 内部系统 / 平台型（判据见 `core-principles.md` 第五节）
2. **受益范围**：一个人 / 一类人 / 公司
3. **需求来源**：老板提的 / 同事传的 / 自己发现的
4. **材料形态**：纯文字 / 图文混排 / HTML 原型 / 在线页面（决定第 8 步能不能做，判据见 `interaction-review.md` 第零节）

分流错了，后面全错。比如把内部系统需求按 C 端的数据标准去评，会得出完全相反的结论。

### 第 1 步：过五问，找空位
逐问核对，不评对错，只标"有 / 无 / 含糊"：

| 问 | 合格标准 | 常见糊弄法 |
|---|---|---|
| 谁 | 具体角色，不是"用户" | "用户希望……" |
| 什么场景 | 有触发条件、发生频率 | "日常工作中" |
| 什么问题 | 现在怎么凑合解决的、代价多大 | 直接跳到方案 |
| 哪些方案 | 复数，含"不做""轻量做" | 只有一个方案 |
| 为什么最优 | 有对比、有证据 | "这样最合理" |

**五问有空位就停在这里。**不往下评方案 —— 因为方案的好坏，取决于它回答的是哪个问题。

### 第 2 步：连问为什么（两层）
- **需求层**：他为什么提这个？他真正要解决的是什么？
- **方案层**：为什么是这个方案？有没有别的？如果必须砍一半，砍哪一半？

【原话】"不停地去深挖，去挑战自己，最终碰撞出一个好的方案。"

### 第 3 步：算账
1. 估人日（没有技术 sense 就先问技术主管，要个大概）
2. × 1000 元
3. 问：**"如果你是老板，你愿意花这笔钱解决这个问题吗？"**

**≤1 人日 → 直接放行，不进入判断。**超过才往下走。

### 第 4 步：边界检查（业务抽象）
- 这次改动会不会影响其他模块？会 → 必须做抽象
- 如果已有模型：这个需求在**水系之内**还是之外？
- 在之外 → 是"不合理"，不是"优先级低"
- 【引申】如果对方拿不出边界，说明他没有模型，只有流程
- 【工具】用 `impact-translation.md` 的翻译表扫一遍文档：哪些话命中 12 个维度，命中的维度「产品层必写」项写了没。

### 第 5 步：找对标（按场景，不按行业）
- 用五问的前三问去检索：谁 + 什么场景 + 什么问题
- 不限行业：做聊天就看游戏对话框、看古早邮件
- 输出：同构案例 / 约束分析 / 哪些是行业惯例、哪些是刻意选择
- 边界：结构和共性可以交给 AI；真实行为必须自己上手用

### 第 6 步：验证设计
- 成功标准定了吗？**做之前就该定**，且随受益范围变（一个人 / 80% 使用率 / 经营数据）
- 埋点埋了吗？埋点是方案阶段的交付物，事后补不了
- 上线怎么让人知道？（内部系统尤其：灰度大概率没人用，但动作必须做）

### 第 7 步：用例覆盖盘点
问：**"这条需求，测试用例会覆盖哪些？哪些是预期不会覆盖、也没人盘到的？"**

因为"极异常情况"的定义就是**大家都没想到**的情况。顺着问永远问不到，只有反向问"哪里没人负责覆盖"才逼得出来。

### 第 8 步：交互关（有图 / 有页面才进）

**前置条件：五问成立，且拿到了图或原型页面。**

五问缺位的，直接停在前面 —— 方案可能整个不做，评交互是白费功夫。

这一步评的是"做出来好不好用"，不是"该不该做"。详见 `interaction-review.md`，四个动作：

1. **对账**：图里有的元素，文字里有没有约束；文字说的元素，图里有没有；状态给全没有。**对账不过，不进规范评审**
2. **列表页**：易搜索、易定位（各六项检查）
3. **详情页**：列「用户想知道」与「我们想让他知道」两个清单，查差集；查操作按钮是否在场景附近
4. **组件**：单行/多行、多行超限策略（不给输 vs 能输标红）、单选/下拉/带搜索下拉/开关的选型

【引申】交互问题按**会不会导致错误操作**排序，不按页面顺序：阻断级（会错数据/不可逆）→ 误解级 → 体验级。

**这一关的取材前提**：给不了图或能打开的页面，只能评"有没有写"，评不了"对不对" —— 这个缺口必须在结论里如实说明。

**先跑取材脚本，别每次手写提取代码**：`python3 <技能目录>/scripts/extract_prd.py <PRD> -o ./prd-extract`（Windows 用 `python`）。它输出 `figure-text-map.json`，每张图带 `confidence`：high 直接采信，medium 回原文核对，**low 或 `caption_shared` 不许猜，回去问人**。脚本只拆料，不评好坏。

### 第 9 步：出结论
四选一，不许模糊：**做 / 不做 / 改完再评 / 待验证**。

配五段输出（见 `assets/review-report-template.md`）：结论、缺的那一问、依据、该问的问题、分发清单。

## 检查项清单（按他的判据推导）

### 状态与流转（源自资金模块的冻结态）
- [ ] 这个对象一共有几种状态？每种状态谁改的、什么时候改？
- [ ] 有没有"在途中"的状态（审批中、处理中、待确认）？钱/货/权在途中时算谁的？
- [ ] 状态能不能回退？回退后已产生的副作用谁清理？

### 覆盖缺口（源自"用例之外的无人区"）

> 【原话·边界】"防重复提交是技术路线，不是产品方案要弄的；部分成功、超时、并发冲突是方案底层的东西，需要系统架构师去考虑。" —— 这些**不进产品方案**，产品经理要懂但不写。

- [ ] 权限：谁能看、谁能改、谁不能看，跨组织/跨层级怎么隔离
- [ ] 空态：没有数据时界面说什么
- [ ] 边界值：数量、金额、时间、字符长度的上限（产品要定，字段表里有「长度精度 / 取值范围」）
- ~~异常流（失败 / 超时 / 重复提交 / 部分成功）、并发~~ → 划归技术层（系统架构师），非产品方案范畴，见上【原话·边界】

### 数据与验证（源自"成功标准前置 + 埋点"）
- [ ] 成功标准是什么？谁定的？什么时候看？
- [ ] 靠哪个数据判断？这个数据现在埋了吗？
- [ ] 数据口径：谁算的、从哪张表来、和谁的口径对得上

### 风险与退路（源自"删节点前先问风险"）
- [ ] 这个需求删掉了谁的环节/权限/校验？它原来在防什么？
- [ ] 出问题怎么回滚？历史数据要不要迁移？
- [ ] 上线范围：全量还是灰度？灰度给谁？怎么通知？

### 业务正确性（源自"表决定业务理解对不对"）
- [ ] 关键实体有没有被当成字段塞进大表？（如把"品牌"塞成商品的一个 varchar）
- [ ] 有没有该独立的对象被合并了？（症状：一堆 `xxx_name`、`xxx_status` 冗余字段）
- [ ] 反向：有没有两个字段的小表，其实只是一个属性？（症状：问"这张表为什么单独存在"答不上来）

### 模块联动影响面（源自"微服务架构意识"）
- [ ] 这个模块的边界在哪？这次改动会突破边界吗？
- [ ] 这个模块和哪几个模块联动？在哪个环节、传递什么数据 / 元数据？
- [ ] 本模块改动的实体 X，还有哪些模块（B、C）也在用？会不会连带受影响、需要额外对齐？

## 常用追问句式

不要用"你觉得这样对吗"，要用**逼出事实**的问法：

- "这个场景多久发生一次？上次发生是什么时候？"
- "现在没这个功能，他们是怎么凑合解决的？代价是什么？"
- "除了这个方案，还评过哪几个？为什么排除了？"
- "如果只能做一半，砍哪一半？"
- "这东西上线三个月后，你靠哪个数据判断它成了？"
- "这个字段以后如果要拆出来，拆得动吗？"
- "这条流程里，运营、财务、法务各自在防什么风险？删了谁接？"
- "这笔钱现在在谁账上？审批中的时候呢？"

## 什么时候停

- 对方开始重复同一句话 → 停，改成让他自己回去想
- 对方开始解释"领导要求" → 停，先回到"谁 + 什么场景 + 什么问题"
- 五问齐全、算账过关、验证可做 → 放行，不要再加戏
