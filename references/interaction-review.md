# 交互评审：图怎么读，文字怎么对，规范怎么卡

业务评审判的是**该不该做**，这一关判的是**做出来好不好用**。两关必须分开过：

- 五问缺位（业务不成立）→ **不进交互关**。方案可能整个不做，评交互是白费功夫
- 五问成立 → 进这一关，逐项卡

> 本文件的标记分三类：
> `【原话】` 本人所述｜`【引申】` 助手推导｜**`【通用】`** 行业通行交互规范，**不是他的话**。
> 第三类必须单独标出来 —— 否则会把通用规范冒充成他的判断，他本人绝不会认。

---

## 零、先取到料：PRD 的四种形态

评之前必须知道自己在评什么。**没取到料就下结论，是最严重的错误。**

| 形态 | 怎么读 | 最容易踩的坑 |
|---|---|---|
| **纯文字**（md / docx / 截图里的文字） | 直接读 | 交互全在文字里描述，信息量最低，几乎所有交互细节都是缺的 |
| **图文混排**（文档里贴图 + 图注） | 读图 + 读图注 + **建立对应关系** | 图和文对不上号（见下节） |
| **HTML 原型**（本地 .html） | 读源码 + 渲染后截图 | 只读源码读不出布局；只截图又看不到 hover / 校验 / 空态 |
| **在线原型页**（Axure / Figma / 内网系统） | 需要浏览器控制，逐页定位 | 定位不到就瞎猜，宁可停下来要链接 |

【引申】取材顺序：**先问"能不能给我能打开的东西"，再谈评**。给不了图或页面的 PRD，交互评审只能评"有没有写"，评不了"对不对"，必须在结论里如实说明这一层缺口。

### 先用脚本提取，别每次重写一遍

`scripts/extract_prd.py` 把 PRD 拆成「文字 + 图 + 图与说明文字的对应关系」。**纯标准库，不需要装任何包。**

```bash
# Mac / Linux
python3 <技能目录>/scripts/extract_prd.py 你的PRD.docx -o ./prd-extract

# Windows（通常只有 python，没有 python3）
python <技能目录>\scripts\extract_prd.py 你的PRD.docx -o .\prd-extract

# 整个目录批量
python3 <技能目录>/scripts/extract_prd.py ./prd文件夹 -o ./prd-extract
```

支持 `.docx` / `.html` / `.md` / `.xlsx`。产出的三样东西里，**`figure-text-map.json` 是关键**：

| 字段 | 怎么用 |
|---|---|
| `nearest_text` | 脚本判断的「这张图旁边的说明文字」 |
| `confidence: high` | 直接采信（有「图1」「截图」「原型」这类明确图注特征） |
| `confidence: medium` | 要回原文看一眼再确认 |
| `confidence: low` | **不许猜**。没找到就是没找到，回去问人 |
| `caption_shared: true` | 一段说明被多张图共用 —— 这本身就是 PRD 缺陷，必须单独报 |

脚本**只做提取，不做判断**。「这个交互合不合理」不进脚本，那是模型的事。脚本也不评好坏，它只负责把图摆到你面前、把可能的说明文字配对好。

**没有 Python 怎么办**（降级路径，不能因为没脚本就停工）：

1. docx / 图片：让用户直接导出 PDF 或截图，或把文档拖进对话
2. HTML 原型：用浏览器打开截图，或让用户给在线链接
3. 实在拿不到图：明说"只能评有没有写，评不了对不对"

脚本也**有它拿不到的东西**：原型页里「点开才出现的标注层」、hover 态、校验报错态。这些必须用浏览器看，脚本拿不到。

### 在线页面怎么定位「图」和「它旁边的说明文字」

【原话·图的两种来源】"这个图呢有可能是他丢了一个 HTML 文件，有可能是我们要控制它的浏览器去帮它定位到具体的页面，然后找到页面旁边的说明文字。"

操作顺序：

1. **先定位页面**：链接直达某个页面 → 记下页面标题或面包屑。不要靠"第几个 tab"记，会错位。
2. **再定位图**：把页面上的图（截图 / 原型框 / 表格）按**从上到下、从外到内**的顺序编号。
3. **再找它的说明文字**：就近搜索 —— 说明文字通常在图的**右侧**或**下方**；原型工具里也可能在**悬浮标注层**或**点击图才展开的面板**里。
4. **配对**：一条说明只对一张图。**一对多或多对一，都要单独标出来**（这本身就是 PRD 缺陷）。

陷阱清单（每条都可能让结论错位）：

- 说明文字标了序号，但页面上图没序号 → 对不上，必须问
- 多张图共用一段说明 → 无法判断哪条约束属于哪张图
- 说明文字描述了图里没有的元素（"点击右上角导出"但图上没有按钮）→ 是 PRD 漏图，不是交互问题
- 页面有多个状态（展开 / 折叠 / 空态 / 报错）但只给了一张截图 → **缺态**，这属于覆盖缺口，要报

【引申】**只评看得见的，不评想象出来的。** 图里没有的控件，不能说"这里应该加一个" —— 那是在替设计师做设计。可以说的是"这里缺一个状态""这个按钮作用的对象不清楚"。

## 一、图文对不上，是第一个要卡的点

【引申】在评任何规范之前，先做一次**对账**：

| 对账项 | 不合格的表现 |
|---|---|
| 图里有的元素，文字里有没有约束 | 有输入框但没说校验规则、没说上限 |
| 文字说的元素，图里有没有 | 文字写"支持批量操作"，图上没有批量入口 |
| 同一元素在两张图里是否一致 | 列表页叫"客户名称"，详情页叫"客户名" |
| 状态是否给全 | 只有正常态，没有空态 / 报错态 / 加载态 / 无权限态 |
| 操作是否有去处 | 有"新建"按钮，但没给新建后的表单页 |

**对账不过，先出对账清单，不进规范评审。** 图和文都对不上，后面评得再细也是评错东西。

## 二、列表页：就查两件事——易搜索、易定位

【原话】"列表页有没有达到易搜索易定位的特性。"

这不是形容词，是两个可以逐项打勾的能力。

### 易搜索

| 检查项 | 不合格长什么样 |
|---|---|
| 有没有搜索入口 | 数据量明显会过百，页面上没有搜索框 |
| 搜的是哪些字段 | 只写"支持搜索"，没说搜名称还是搜编号、搜不搜备注 |
| 模糊还是精确 | 输入"阿里"，能不能搜到"阿里巴巴" |
| 多条件能不能组合 | 搜索和筛选是互斥的还是能叠加，PRD 没写 |
| 搜不到怎么反馈 | 空结果页说什么？是"没有数据"还是"没找到，试试去掉筛选条件"——这两句差别很大 |
| 命中能不能看见 | 关键词要不要高亮，列表里哪一列是被搜中的字段 |
| 查询的 key 列表里有没有对应展示 | 能按"编号"搜，列表却没有"编号"列——查到了也对不上号、确认不了是不是这条（【原话】查询能查的，列表得有对应展示） |
| 筛选项有没有按频率分层 | 一堆筛选项平铺，高频低频全露；或高频的被藏进"更多"（【原话】高频前置、低频收起/可配置） |

### 易定位

| 检查项 | 不合格长什么样 |
|---|---|
| 有没有筛选 | 只能靠翻页找 |
| 有没有排序 | 默认按什么排、能不能改，没写 |
| 分页还是滚动加载 | 两种都存在，但没说选哪个、每页多少条 |
| 定位后能不能留住 | 翻到第 5 页点进详情，返回时回第 1 页还是第 5 页（**这条最常被漏**） |
| 关键信息在不在列上 | 用户是靠哪一列判断"就是这条"的，那一列在不在首屏可见范围内 |
| 字段优先级排过没有 | 十几列按表结构顺序平铺，用户认人的核心字段被挤到屏外；没按"概率最大的场景"排序、没做视觉聚焦（【原话】字段按概率最大场景优先级排序 + 视觉聚焦） |
| 一行太长怎么处理 | 名称超长是截断加省略号、换行、还是撑开列宽 |

【引申】**易搜索易定位的本质是同一个问题：用户能不能在 3 秒内确认"我要的那条在不在里面"。** 所有检查项都是在回答这一句。

【引申】列表页最常见的两个深层错误：
1. **列的信息密度错配** —— 放了 12 列，用户真正用来认人的只有 2 列
2. **操作放在行尾一个"更多"里** —— 高频操作被折叠，等于没有（与详情页"操作按钮是否在相关场景附近"是同一条判据，见下节）

## 三、详情页：两个清单的差，就是设计战场

### 第零步：先查"进没进错"——承接列表页

【原话】"详情页最核心是对列表页的承接。给用户一个感觉：你从这个地方进来的，你没进错。列表页的关键信息到详情页要承接、或直接展示出来。"

| 检查项 | 不合格长什么样 |
|---|---|
| 列表页的"认人字段"详情页承接了吗 | 列表页靠"客户名称 + 负责人"认人，详情页标题区却没有，或藏在字段堆里，用户得找半天才能确认没进错 |
| 前置入口的信息带没带过来 | 从"待跟进"列表点进来，详情页没任何"待跟进"的状态标记 |

### 第一步：列两个清单

【原话】"我们得去思考，在这个场景下，用户想要知道的信息是什么？我们想让用户知道的信息是什么？对应的操作按钮是不是在相关的场景附近。"

| 清单 A：用户想知道 | 清单 B：我们想让他知道 |
|---|---|
| 他打开这个页面是为了做什么决定 | 我们要传达的规则、风险、状态 |
| 他判断"能不能往下走"需要哪几个字段 | 我们担心他误操作的地方 |

**A 和 B 不一致的地方，就是这个页面的设计重点。** 完全一致 → 说明没想过；完全不一致 → 说明在跟用户对着干。

【引申】三种典型错配：
- **A 有 B 无** → 用户要的信息没给，他会去别处问（找同事、打电话、翻聊天记录）
- **B 有 A 无** → 塞了一堆我们想说、他不关心的字段，把关键信息挤到折叠区
- **两边都漏了状态** → 钱在哪、单到哪一步了、谁在等谁，这类"过程态"经常两边都没列

### 第二步：查操作按钮的位置

【原话】"对应的操作按钮是不是在相关的场景附近。"

【原话】"整个详情页都可能用到的按钮，置底漂浮、始终可见；只有锚定到某个字段/区块才用到的，放到它相关的地方。一定要考虑按钮 action 的相关性。"

| 检查项 | 不合格长什么样 |
|---|---|
| 按钮是否靠近它作用的对象 | 改某个字段的操作，放在页面底部通栏，离那个字段两屏远 |
| 全局动作有没有始终可见 | 保存/提交这类全页都会用的按钮，只放在页面某处，用户滚下去就找不到了（该置底漂浮） |
| 按钮作用的范围是否清楚 | 一个"提交"，到底是提交整页还是提交这一块 |
| 该有的操作有没有 | 能进来、不能改；能改、不能撤回 |
| 危险操作有没有隔离 | 删除和保存并排、同色、同样大小 |
| 操作后去哪 | 点完是原地刷新、跳列表、还是弹窗关闭，PRD 没写 |
| 不可用状态怎么表达 | 条件不满足时按钮是置灰、隐藏、还是点了才提示 |

【引申】**"按钮在场景附近"是就近原则**：操作离它作用的对象越远，用户越容易搞错自己在操作什么。通栏按钮只适合"整页级"动作（保存整张表单、提交整单）。

## 四、表单与组件：场景决定用哪个

### 4.1 文本：单行还是多行

| | 单行 | 多行 |
|---|---|---|
| 判据 | 内容不会换行，且通常较短（名称、编号、标题） | 内容天然分段，或会被复制粘贴一大段（备注、描述、驳回原因） |
| 常见错误 | 用单行装"说明"，用户看不到自己输的后半段 | 用多行装"名称"，白白占两行高度 |

### 4.2 多行文本超限：不给输，还是能输但标红

【原话】"多条文本它有没有带这种超出这个字符限制的交互规范 —— 到底是不给输了，还是说能输但是变红。"

这是**必须二选一并写清楚**的一条。PRD 里只写"限制 200 字"是不合格的 —— 那句话没说清超了会怎样。

| 策略 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **硬限制** | 到上限就输不进去（maxlength） | 内容可切分、用户能自己截断；上限是硬性业务规则（如身份证号） | 用户粘贴一段长文本，会被**静默截断**，他不会发现 |
| **软提示** | 允许继续输，超出部分标红/计数变红，提交时拦住 | 内容是用户的表达（备注、驳回理由），需要他看到全文才能决定删哪句 | 要在提交处做阻断，且必须写清报错文案 |

【通用】两种都合规，但**必须有明确选择，且要写清超出后的表现**（字数计数器在哪、红在哪、能不能提交、报错说什么）。

【引申·选址判据】问一句就能定：**超出上限的那部分内容，用户自己能不能判断该删哪句？**
- 能（备注、说明）→ 允许输完再标红，让他自己裁
- 不能（编号、金额、日期这类不该有"多余部分"的）→ 直接不给输

【引申】硬限制有个隐蔽坑：**粘贴截断是静默的**。用户从别处复制 500 字粘进来，只进去 200 字，界面不提示，他会以为全进去了。所以选硬限制时，PRD 必须写"粘贴超长时的提示方式"。

### 4.3 选择类：单选、下拉单选、带搜索的下拉、开关

【通用】控件与场景的匹配有共识，看**三个变量**：选项数量、用户是否知道自己要选哪个、改动是否立即生效。

> 下面这张表是按三个变量整理的【通用】共识。**但表格之下带【引申】的句子是助手加的判据，不是通用规范** —— 两者不许混着引用。

| 控件 | 什么时候用 | 什么时候不该用 |
|---|---|---|
| **单选（平铺 radio）** | 选项少（一般 ≤5）、需要让用户看到全部可能性 | 选项多，撑满屏幕 |
| **下拉单选** | 选项多、用户心里有数、且选项集合稳定 | 选项少时用它（多一次点击，还藏了信息） |
| **带搜索的下拉** | 选项很多（几十上百）、用户**知道关键词** | 用户不知道叫什么、只知道"大概是那个" —— 他搜不出来 |
| **开关（switch）** | 二元状态，**拨动即生效** | 需要点"保存"才生效的二选一（这时该用单选或勾选） |

【通用】超过多少条该上搜索，业界无统一阈值，按"用户能不能靠滚动在 3 秒内找到"判断。**不要编一个具体数字写进规范。**

【引申】**开关最常被误用**。判断只需一句：**拨完这一下，服务端是不是马上变了？**
- 是（启用/停用、上架/下架）→ 开关
- 否（表单里的性别、类型、是否开票）→ 单选或勾选，跟表单一起提交

用错的后果很实在：开关放在表单里，用户拨了以为保存了，其实没提交，回头发现没生效。

### 4.4 通用的四个必查项

不管什么组件，这四条 PRD 里都得有：

1. **必填 / 选填** —— 有没有标、提交时怎么提示
2. **默认值** —— 有没有、默认值合不合理（默认选中的那个，用户大概率不会改）
3. **禁用态** —— 什么条件下不可用，不可用时是置灰还是隐藏（**隐藏会让用户以为功能不存在**）
4. **校验时机** —— 失焦校验、实时校验、还是提交时统一校验，三者的体验差别很大
5. **报错文案指路** —— 不能只说"格式不对"，要说出"正确的格式是什么"；且要短到一眼能懂（【原话】）
6. **提交提示优先级** —— 多个错误同时报时，先报哪个后报哪个排了吗？能一个弹窗装下的，别弹五下（【原话】）

## 五、交互缺陷怎么报

【引申】每个问题按四段报，**一段都不能少**：

1. **位置**：哪个页面 / 哪张图 / 哪个控件（精确到能让他一眼找到）
2. **现象**：现在 PRD 写的是什么（引用原文或指向图）
3. **违反的规范**：属于哪一条（列表页易定位 / 就近原则 / 开关即时生效…），并标 `【通用】` 还是 `【原话】`
4. **用户会怎么错**：具体到什么人在什么场景下会做什么错事

第 4 段是关键。**说不出"用户会怎么错"，就不是一个成立的交互问题，只是一个风格偏好。**

示例：

> **位置**：客户列表页（图 2）
> **现象**：12 列全部平铺，无筛选、无排序，只有分页
> **违反**：列表页「易定位」—— 定位后能不能留住、关键信息在不在列上
> **用户会怎么错**：销售要找"上周签的那家"，只能一页页翻；翻到第 4 页点开详情，返回后回到第 1 页，得重新翻一遍。一天做 5 次，每次多花 2 分钟。

### 报告分层

交互问题多的时候，按**会不会导致错误操作**排序，不要按页面顺序排：

| 层级 | 判据 | 处理 |
|---|---|---|
| **阻断级** | 会导致数据错、钱错、操作不可逆 | 必须改完再上 |
| **误解级** | 用户会理解错，但错了能发现能改 | 建议本期改 |
| **体验级** | 多花几步、多等一会儿 | 可以进池 |

---

## 六、不许做的事

- **不要替设计师做设计。** 不画交互稿、不写"应该改成左右布局"这类成品方案。给规范和后果，改法让他自己出（硬规则 10）
- **不要用通用规范压他的业务判断。** 规范是默认值，业务约束优先 —— 但业务要给出理由
- **不要把风格偏好说成违规。** "我觉得这个按钮太小"不是问题；"这个按钮点了会删数据，但和保存按钮同色同大小"是问题
- **不要评图里没有的东西。** 缺的控件属于"缺"，不属于"错"
- **不要编数字阈值。** 超过几条要搜索、字符上限设多少，这类必须问业务方，不能替他们定

## 七、他还没给判据的地方（如实标空白）

- 各控件的**具体阈值**（选项条数、字符上限、列宽）—— 他不给数字，只给判断方法
- **移动端 / 小程序的交互规范** —— 只谈过 Web 端场景，移动端未涉及
- **无障碍 / 国际化**（读屏、RTL、多语言文案长度）—— 未涉及
- **设计系统 / 组件库** —— 未提到是否有统一的组件库约束

遇到以上四类，如实说"这块他没给判据"，不要拿通用规范冒充他的标准。
