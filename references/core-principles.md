# 判断内核（原话与推导）

每条标注出处：`【原话】` = 本人所述；`【引申】` = 助手推导，未经本人确认，可被推翻。

---

## 一、业务理解的五问主链

【原话】"了解业务的前提，最核心的一句话就是：谁在什么场景下遇到了什么问题，那么基于这个点我们提供了哪一些解决方案。那为什么你这个解决方案是被当作目前最优的方案来进行评审的。"

- 前三问是事实陈述，第四问要求**复数**（方案不止一个），第五问是主战场。
- 【引申】五问不全时，不评第五问。缺的是哪一问，就直接说缺哪一问。
- 【引申】"谁"必须落到具体角色；至少要落到"一类人"，跨部门时上升到"公司"。

## 二、连问为什么（问题深挖）

【原话】"我自己最核心的方法论是问为什么……遇到任何问题都要多问自己一个为什么。"

两个作用点，不可合并：

1. **需求进来时**：用户提了这个需求 → 他为什么会提？他核心想解决的问题是什么？
2. **方案出去时**：为什么我的方案是这样？有没有可能有别的方案？

【原话】"实际上就是要不停地去深挖，去挑战自己，最终碰撞出一个好的方案。"

【引申】关键是**对自己**追问，不只是追问业务方。多数人把"问为什么"理解成盘问需求方，真正的差距在挑战自己的方案。

## 三、业务抽象

### 触发判据
【原话】"如果这是一个新的模块，或者说是一个新的产品，它必做业务抽象。然后现有产品的迭代也可以做业务抽象，核心就是你的这一次改动会不会对其他模块产生较大影响。如果有的话就得做。"

【引申】扳机是**影响面**，不是复杂度。两种情形是同一件事：现有框架即将装不下 —— 新建时没有框架要造一个，迭代时框架被突破要改一个。

【引申】抽象发生在**"要变成系统"的那一刻**，不是"要开始做业务"的那一刻。0→1 阶段先跑业务、不抽象。

### 动作（四步）
【原话·拳皇例】两个人 → 有手有脚（出拳出脚）、有大招、有上下左右 → "抽象到这，大家其实对这个游戏都有概念了" → 基于抽象看限制："我限制了两个人，那也就意味着我后面只能做对打游戏"、"只有上下左右，它是没有空间属性的，也就意味着它只能在平面上移动，没有 3D"。

1. 找实体（这套业务里有几个东西）
2. 挂属性（每个实体上有哪些能被操作的东西）
3. 得模型（合格线：行内人听完脑子里有画面）
4. 推边界（拿未来设想逐个代入，塞不进去处即边界）

【原话】"它有点像数学建模，放到一套模型里，你可以根据这个模型里面的一些关键节点来推演出你未来这套产品的边界在哪。"

### 两个实例的方向不同
- **拳皇**：先建模型，再推边界（前瞻）
- **资金模块**：撞到反例，再修模型（修正）

【原话·资金例】表面是顺序流程：出账单 → 客户打钱 → 走请款 → 钱不够垫款、够就出款。深入调研后发现：客户会多打少打；账单里有风险保证金（押金，不属营收，要还客户）；押金按人收（员工工资的一定比例）；人员流动要把张三的押金转给李四。

【原话】结论："单靠一个顺序的流转的业务流程是不够的，你一定得有一套资金体系"，"项目上得挂资金，供应商得挂资金，人员上得挂资金，资金还有币种的限制"。
【原话】核心抽象："资金其实本质上它就是进和出，就是基于不同账户的进和出，但是它会有冻结态……资金在进行审批的过程当中，它就是一个被冻结的状态。"
【原话】效果："后续不管我们业务流程怎么变，只要还有钱在流转，都能够吃得进去。"
【原话】落点："每一个实体都会挂一个资金账户。"

**招式一（最可复用）：把「流程中的一步」升级为「实体共有的能力」。**
资金原本是出款环节里的一步，抽象后变成"任何实体都挂账户"。位置从时间维（流程节点）移到空间维（实体属性），扩展性由此而来。【引申】

**招式二：从「顺序流程」换成「账本」。**
业务流程会变，但钱从 A 账户到 B 账户不变。所以他借的是银行、会计那一套，而非描述业务步骤。【引申】

**冻结态的点睛**：只抽象"进/出"两态时，"审批中的钱"无处安放；加"冻结"才闭合。属性从 2 变 3，是因为现实里存在"钱在途中"。【引申】

### 抽象层次的判据（重要）
助手提议再往上抽到"额度与占用"以覆盖积分 / 预授权 / 信用，被否决。

【原话】"不能啊，因为积分是积分，预授权额度是额度，信用额度是信用额度……你可以理解成它们是三个仓库，但是并没有一条水流会经过这三个仓库。"
【原话】"客户的项目账户、供应商的账户、人员的币种账户，它都是钱都会流来流去，都是在这些账户里面转的。"

- 判据不是形态相似（都有账户 / 进出 / 冻结），而是**是否存在一条水流穿过它们**。
- 【引申】**抽象层次不是越高越好。抽到"能覆盖一切"那层，通常已经抽过头了** —— 会得到一个能装一切但装不准的模型。
- 【引申】正确的高度 = 能找到一条共同的流。边界是**水系的边界**。
- 【引申】硬门禁：合并两个概念前先问"它们之间会发生流转吗？"若答案是"需要中转 / 兑换 / 审批"，即两条水系，不可合并。
- 【引申】币种不是另一个仓库，是同一条水系里的分河道（跨河道要结汇）。

### 属性的两类
【引申，待校验】
- **可变状态**（进 / 出 / 冻结）→ 构造能力
- **约束维度**（币种、挂载实体）→ 划定边界

### 抽象的验收价值
【引申】推不出边界的抽象是失败的抽象。可推演性 = 建模质量。业务抽象的产物是**心里的 ER 图**，它的用途是给"看表"提供比对基准 —— 不是为了文档好看。

## 四、技术 sense

【原话】"我会要求产品经理有技术 sense……前端的请求响应、事件监听机制，前后端怎么样通过接口去传递信息，长链接和短链接，后端的话 MVC 设计模式，controller 层、service 层、dao 层。"
【原话】"技术评审的时候，核心评两块，第一个是接口，第二个是表，表决定了这个业务大家的理解对不对，扩展性对不对。前端接口的话，主要确定的是这个业务形态大家有没有理解正确。"
【原话】"他需要去了解，但他不需要去设计。"

【原话·边界补充】"我不会专门在产品方案里说防重复提交的问题，这是个技术路线，不是产品方案要弄的。部分成功、超时、并发冲突这些，也不是现阶段产品经理需要去考虑的内容，它是整个方案底层的东西，需要系统架构师去考虑。"

【引申】这条把"了解但不设计"再往下压一层：**不但不设计，连方案里都不写**。防重复提交 / 部分成功 / 超时 / 并发，是系统架构师的技术层，产品经理要能听懂、能判断影响，但不写进产品方案。
【原话·唯一越界许可】"如果产品经理对这个产品未来的规划有 sense……他能想到后面三个版本四个版本的迭代，那他就可以去跟技术有要求：后续会发展成这样，所以这个字段我建议应该怎么样去设置。"

### 模块边界意识（微服务架构的意识）

【原话】"产品经理不管是评审文档也好、写文档也好，一定要有类似微服务架构的意识。我做这个模块，我得知道我的模块边界在哪、我这个模块和哪几个模块要联动、在什么地方要联动、联动的值是什么——是哪些数据或者元数据产生了联动。"

【原话】"这样子他对系统整个构成及自己所负责的边界会非常了解，后续如果有需求能够突破边界，他也能第一时间知道该找谁响应、找谁协同。"

【原话·评审例】"评审方案的时候也一样。比如模块 A 要影响实体 X，但模块 B 和 C 又跟实体 X 相关，所以当我这个模块要影响实体 X 的时候，我得意识到它对模块 B 和 C 也会有影响——这是评审时需要额外去对齐的东西。"

【引申】这是"业务抽象"里影响面判据（见第三节）在模块层面的落地：抽象看的是"这个改动会不会突破模型边界"，模块意识看的是"这个模块改某个实体，会波及哪些模块"。写文档写清四件事——① 模块边界；② 联动哪些模块；③ 在哪个环节联动；④ 联动传递什么数据 / 元数据。评审时多查一步——影响实体 X 时，还有谁也在用 X。

### 看表三步（技术评审实操）
【原话】"我会先看表的命名……先得知道他们有哪几张表，大概通过表名我就能知道每张表承担的作用是什么。然后因为我脑子里面其实已经有 ER 图了，我能够根据表名知道他有没有把关键的属性当实体，或者把关键的实体当属性。那么如果遇到这样的偏差我就会问他们，为什么这么设计。"

1. 看表名 → 有哪几张表、各承担什么
2. 与自己心里的 ER 图比对 → 找错配
3. 遇到偏差就问"为什么这么设计"（不问"为什么错了"）

【引申】两类错配的症状：
- 属性被当成实体 → 表变碎，一堆两三个字段的从表，关联链长；问"这张表为什么单独存在"常答不上来
- 实体被当成属性 → 表变胖，大表挂满 `xxx_name` / `xxx_status`，同一信息多处出现

【引申】问完之后分三种处理：
1. 对方没想过 → 缺口，用问题引导
2. 想过且理由是**业务原因** → 改自己的模型
3. 想过但理由只是**实现省事** → 该拦

即：要区分"有理由"与"合理由"。

## 五、终端类型（四类）与受益范围

### 四类终端判据

**C 端**
【原话】"核心是要看数据，我们需要客观地基于数据给反馈，因为用户量太大，我们不可能模拟成每一个用户。"

**B 端**
【原话】"核心就是业务抽象，尽可能做 B 端产品的通用性，当然也要找到我们目标客户的核心需求，基于核心需求去发散。"
【原话·背景判断】"中国的 SaaS 做不起来，实际上都把 B 端产品做成了外包。"

**内部产品**
【原话】"很多产品经理最容易犯的错就是，他们太把自己当成一个解决方案工程师了，用户提需求他们就去解决，巴不得有人给他们提需求，因为有需求就有活干。但核心的问题是我们要站在公司的层面考虑这个需求该不该做。"
【原话·成本理由】"可能只是某一个人提了一个解决他个人效率的需求，但是我要投的产研资源远比招两三个人的成本要大。"
【原话·第二个理由】"也得考虑我做了这个东西对于系统后续迭代有没有影响。"

**平台型（双边）**
【原话】"算平台型产品吧……双边本身就比较难搞。"
【原话·判据】"站在平台的角度，此时到底是要偏袒供给方还是需求方。因为平台本身就是要维持双边的平衡，就像水多了加面，面多了加水一样。"
【原话·例子】"我做的是电商平台，我手里面有一堆商家和极少数消费者。那此时我优先保障的应该是什么？应该是商家的利益，因为商家多，我要让商家尽可能留在我们平台……买家的一些售后问题我可能就不会考虑，商家就算卖了商品出现一些残次，我大概率也会偏袒商家。"
【原话】"但是假设有一天商家、平台的用户变多了，超过了这个平衡，那我就要开始去做商家的管控了。"
【原话】"这是个动态平衡机制，得根据当前的场景，我该听谁的、我该偏袒谁。"

- 【引申】操作化：先判**哪一侧稀缺 / 不足**，偏袒稀缺侧，接受富裕侧部分体验受损；稀缺侧反转时，偏袒方向必须跟着反转。
- 【引申】注意它反直觉：消费者少的时候平台反而偏袒商家。这不是"用户至上"失效，而是"平台的约束在稀缺侧"。
- 【引申】平衡点移动的预警：补贴成本上升、某侧服务质量下滑、投诉集中 —— 都在提示该换边了。

### 受益范围三档（决定"该不该做"与"怎么算成"）
【原话】"产品经理他的视野到底是解决某一个人的问题，还是某一类人的问题，还是公司的问题。"
【原话·经典反例】"所有销售都觉得商务合同审批流程是复杂的，他们都想简化，但正是因为公司管理的要求，需要让某些部门节点的人介入：运营部去审核填没填对，财务部去审核账号填没填错，法务部审核合同风险。如果我们单一地只解决销售团队的问题，那整个公司的风险就会上升。"

| 粒度 | 要什么证据 | 默认动作 |
|---|---|---|
| 一个人 | 无 | >1 人日先找替代方案（招人 / 手工 / 买工具） |
| 一类人 | A / B / C / D 多方样本，看共性与差异 | 可进入方案设计 |
| 公司 | 被影响的每个部门都要点头 | 上升到公司层面讨论 |

【引申】针对"简化流程"类需求加一条硬检查：**删节点前先写清每个节点在防什么风险、删掉后谁承担。**

## 六、算账与顺手额度

【原话】"我们不会算得这么明细。我经常问我下属一个问题：如果你是老板，你觉得……"
【原话·流程】"让他评估做这个需求大概要多久、大概要花几个研发。如果没有技术 sense，可以找技术主管先聊一下，聊个大概的时间。然后我们按照一人一天 1000 块，比如说一个需求需要五个人日，那就是 5000 块。那 5000 块就很简单：如果你是老板，你愿意花 5000 块解决这个问题吗？就出来了。"
【原话·顺手额度】"顺手人情的额度就是一个人日差不多。"
【原话·不要过度评估】"有些时候我们不能过度地去评估一个需求的价值。很多日常级别的需求是顺手做的事，虽然只解决你个人问题，但我顺手就能做掉，我也愿意做个顺手人情。"

- 三步：估人日 → ×1000 元 → 问"如果你是老板愿不愿意花这笔钱"
- 【引申】二分线：**≤1 人日顺手做，不进入判断；>1 人日进入算账流程。**
- 【引申】"给视角，不给标准"—— 与带人时"不告诉你该怎么改、让你自己想"是同一个招式，用了两次。
- 【引申】不做精细 ROI 表。做细会增加摩擦，反而没人用。

## 七、需求来源、需求池与排序

### 三类来源 = 三种失真
| 来源 | 失真在哪 | 动作 |
|---|---|---|
| 老板 / 上级 | 信息不对称：他掌握的信息源天生比你多，且不会主动解释 | **先问清原因**。姿态是"为了把这件事做好，我得弄明白"，不是质疑他 |
| 同事传递 | 利益驱动：有人为了让你排上，会故意把情况说得很严重 | 多方论证 + 靠业务理解校验，把"严重"落到数据和样本上 |
| 自己发现 | 盲区：只看得到自己链路内的问题 | 进池，与其他来源比对 |

【原话·硬规则】"他跟不跟我说是他的事，我问不问是我的事。"

### 需求池
- 【原话】"我们都会把需求沉淀到需求池，定期进行需求池的盘点。"
- 四分类：马上要做 / 后面做 / 短期不考虑 / 不合理
- 【原话】盘点频率：**每月一次**
- 【引申】边界清单可直接服务这个分类 —— "不合理"往往不是需求坏，而是**落在边界外**。

### 排序
【原话】"目前其实是靠我去决策的……因为我会参与需求的排期，所以这个是我的判断，它不是我产品经理需要具备的能力。"
【原话·但】"首先得有足够多的信息。两个部门的需求撞车，我会先做跟我关系比较好的那个部门的……我得让他们知道，跟我关系好有点好处，这个也很正常对不对。"

- 【引申】**"排序权不在你手上时，别去争这个"** —— 产品经理的任务是让信息足够充分、成本算清楚，交给能兜的人。
- 【引申】关系资本是"存—取"结构：顺手人情是存款，抢资源时优先是取款。有存才有取。这也解释了"有标准的拒绝 + 有额度的顺手"为什么能长期成立。
- **可迁移性提示**：此条成立前提是他参与排期、有兜底权、有人缘。不可写成"优先关系好的部门"作为普适规则。

## 八、成功标准、埋点与未达标

【原话】"这个东西应该是在确定要做这个需求的时候就得去思考：我现在要解决这个问题，做这个需求，怎么样才能验证这个需求是成功的？"
【原话·随受益范围而变】"有可能这个需求是张三提的，那张三觉得能解决他的问题就是成功；也有可能我这个需求解决的是一堆人的问题，可能有 80% 的人使用了这个功能就算成功；还有一些做 C 端的，就要更多地直接反映在经营数据上。"
【原话·验证节点】"我的方案里面一定要留下足够被它验证的一些闭环节点，比如说我要验证这个东西的使用率，那我肯定得做一些数据埋点才能验证。"

- 【引申】埋点事后补不了，所以它是**方案阶段的交付物**，不是上线后的事。
- 【原话·未达标】"目前来说没有这种没达成目标怎么复盘的规范化工作案例……在我的概念里面，产品经理需要有 sense 去跟踪自己以往上线产品的复盘情况，如果没达到预期，是需要重新归到需求池里面的，相当于再走一个轮询。"
- 【引申】回池的最小闭环：立项写死成功标准 → 到期回看 → 未达标回池并**必写一行"当初哪里判断错了"** → 按五问重判。不归因就回池 = 把同一个坑再踩一次。
- **标注**：这块是薄弱区，机制未落地，不要编造流程。

### 上线流程（内部系统）
【原话】"发布之前一定会让相关业务方去进行一些使用。"
【原话】"目前灰度环境开放受资源限制，所以大版本风险很高的，肯定会开个灰度环境让他们先用用，但他们大概率不用，但这个动作我们得做，不然的话改的太多，他们说没提前跟他们说。"
【原话】"如果小功能呢，我们就会采取发上线说明或者做线上培训这样的方式，去把这个功能传递到位。"

- 【引申】此处的灰度主要承担**知情权兑现与免责**，不是风险验证。评审时应问"这次上线怎么让人知道"，而不只是"灰度测出什么"。

## 九、出了事怎么办

| 场景 | 回答 |
|---|---|
| 上线炸了 | 【原话】"一般都是测试团队的责任" —— **但见下方更正** |
| 做完没效果 | 【原话】"如果方案是我这边过过的，也投了非常多的资源，那当然是我承担责任；如果是方案我没过过又投了很多资源，这种情况也不会（发生）" |
| 判断被证明错了 | 【原话】"你就改呗" |

### 更正的归责机制
【原话】"我们允许每一个人犯错，我允许 PRD 漏东西，我也允许测试没测出来。但是一旦上线，如果这个东西是在测试用例里没测出来的，那就是测试的问题；如果这个东西都不在测试用例里，那只能证明一件事，就是它是一个极异常的情况，产品和测试都没盘出来，那这种情况只能一起背锅了。"

- **判据不是"谁能力不足"，而是"测试用例里有没有"。**
- 【引申】测试用例是团队责任分界的契约：它界定的不是"该测什么"，而是"我们说好要覆盖什么"。用例之外即无人区。
- 【引申】归责看**约定**，不看能力。追的是"我们有没有约定过"，不是"你尽不尽心"。
- 【引申】"允许犯错"与"共同背锅"是配套的：前者让人敢暴露问题，后者让系统性盲区不被个人化。过程宽容、结果清晰。
- 【引申】评审最后一关：**"这条需求，测试用例会覆盖哪些？哪些是预期不会覆盖、也没人盘到的？"** —— 极异常情况只能这样逼出来。
- 【引申】责任绑定决策权，前置条件是**决策留痕**：每次评审记下"谁拍板、依据是什么"。

## 十、协同

【原话】"AI 日益发展的今天，个人能力会变得非常强，团队规模一定会急剧变少，那么在小团队的情况下，信息的互通就变得尤为关键。"
【原话】"这个信息的互通不仅仅作用于我得让你知道我知道的，后续对于 AI 去读团队的知识库、读团队的共有资产也是很重要的一环。"
【原话·两条自检】"你去做一个决定，你有没有思考到通知到该通知的人？以及你要去思考，我告诉人哪些信息，目的是什么。"

三条落地：
1. **通知覆盖**：该知道的人是否都知道了
2. **信息目的**：告诉谁、说哪些、为什么 —— 不是倾倒
3. **机器可读**：产出默认可入库，否则明年 AI 读不出东西

【引申】评审结论必须带分发清单（对象 / 说什么 / 目的 / 渠道）。

## 十一、文档

【原话】"很多人都会说'我们团队有写文档的规范'，但实际上我觉得对于任何文档，我们也需要去思考写文档的目的是什么。"
【原话·AI 之前的三类读者】产品团队（需求原来是什么样、什么情况下要变成什么样、逻辑是什么）、开发（能很好读懂）、设计（能找到 UI / UE 的关键点）。
【原话·形式】"能用表说清就用表，能用图说清就用图。"（不限于 Axure）
【原话·交互说不清时】"请参照什么 App 或者什么网站的什么功能，给一个链接"；或"直接用 AI 生成一个 JS，你直接用这个 JS 就可以了"。
【原话·AI 时代新增】"第一个是要让 AI 能看懂；第二个是当我们去做评审、团队沟通这个项目的时候，得让大家知道这个项目发生了什么事情、做了哪些变更。"
【原话·终极三问】"我写文档的目的是什么？是给谁看的？他看这个文档的目的是什么？"

【引申】载体按歧义度递减升级：文字 → 表格 → 图 → 参考链接 → 可交互原型。判据不是规范，是"这个读者靠它能不能复原我的意图"。
【引申】"让 AI 能看懂"是个很严的质量标准 —— AI 读不懂的，人往往也读不懂。

## 十二、特质与主动性

### 特质优先于能力
【原话】"产品经理的能力可以稍微弱一点，但他们得具备一些特质。"
【原话·知错就改】"有的产品经理为了维护自己所谓的权威，可能会一条路走到黑，错的也硬着头皮去说……到后面大家都不跟你争就无所谓，然后很有可能出现迭代不下去的情况。"
【引申】关键转折不是"你错了"，而是"大家都不跟你争" —— 反馈通道关了，此后所有方案都失去纠偏机会。
【原话·时间承诺】"我不太会喜欢跟别人定一个 Deadline……更多的是让大家自己去说你觉得这个东西要多久，但是只要是你自己说出的时间，那就得按照这个时间完成。"

- 【引申】授权换承诺的刚性：责任从"外部强加"变成"自己承诺"，失约没有借口。
- 【引申】时间不只是排期工具，也是**能力与态度的信号**。

### 勇于做坏人
【原话】"产品经理是要勇于去做坏人的……你要学会去拒绝，学会去让别人不舒服。很多人很难突破这一点，都习惯当老好人，不愿意去起冲突。"
【原话·关键约束】"这些东西不能是产品经理或团队管理者埋在心里的东西，你得把'我团队需要什么样的人'放上来。"

- 【引申】"敢做坏人"成立的前提是**标准公开**：拒绝的依据是公开标准，不是个人好恶。这也是它不与"不制造恐慌、不搞小团体"冲突的原因。

### 主动性
【原话】"产品经理要站在公司至少是 VP 的视角看这件事情，看所有的问题。你要去协同一切能够让公司变得更好的资源，也要去尽可能拒绝浪费公司资源的一些行为……而不是做完一两个需求。"

- 【引申】主动性不是勤快，是**视角层级**。它为整套判据提供最高裁决者：**公司利益**。
- 【引申】边界在"专业判断"上（谁专业听谁的），不在"结果责任"上（公司层面的后果归产品经理）。
- 【引申】只把需求做完的产品经理，在这里是不合格的 —— 哪怕需求做对了。

### 四条底色：聪明、乐观、皮实、自省

【原话·精神来源】"我特别欣赏阿里有一段时间的价值观，就是聪明、乐观、皮实、自省。"
【原话·落点】"特别是……接受不了批评，接受不了错，逆商吧也不够皮实，所以这个我觉得是我对产品经理一点软技能上的要求，就是他必须得皮实。"

四条里**他只对「皮实」给过具体判据**。其余三条如实标空白，不替它编 —— 编出来的"乐观 = 积极向上"这类话，既不像他，也没法用来评人。

| 底色 | 他的判据 | 出处与状态 |
|---|---|---|
| **聪明** | 间接：要求"花 10 秒盘出大致框架和风险点"；同时又说过"能力可以稍微弱一点" | 【引申】指向**想清楚的速度**，不是 IQ。无直接原话 |
| **乐观** | 无 | **空白**。不要引申成"心态积极""传递正能量"这类空话 |
| **皮实** | 判据完整，见下节 | 【原话】 |
| **自省** | 间接：上线未达标要回池，并写一行"当初哪判断错了" | 【引申】；完整复盘流程他还没给，见"未达标"空白项 |

【引申】"聪明"与"能力可以弱一点"不矛盾：他要的是**判断力**（把事想清楚的速度），不是**实现力**（工具熟练度、技术细节）。前者是入场券，后者可以补、可以靠团队补。

### 皮实：逆商是入场券

【原话·病灶场景】"我经常会遇到团队的一些小伙伴，有一个文档好不容易写完了，但写完之后发现有问题、可能得推倒重来，整个人就很崩溃，或者说不想改。"
【原话·定性】"但这样是不对的。接受不了批评，接受不了错，逆商吧也不够皮实。"
【原话·时代背景】"因为这个时代进步太快了，信息太多了，肯定会有犯错的时候，我们得去接受自己的错误。"
【原话·标准动作】"出了问题我就认，有错我就改，快速地调整状态，收拾行囊重新出发。"

**【引申】皮实的定义（从他的场景反推）**

不是脸皮厚，不是不在乎，是**在沉没成本被清零的那一刻还能继续干活**。

拆开看这个场景里到底发生了什么：

- 写完了要推倒重来 → 痛的是**沉没成本**，不是方案本身
- 崩溃 / 不想改 → 把"我的方案错了"读成了"我这个人不行"
- 皮实 = 能把这两件事**分开**

**【引申】皮实与"知错就改"是上下游，不是同一条**

| | 知错就改（已有） | 皮实（本次补充） |
|---|---|---|
| 时点 | 被质疑**当场**的反应 | 错已成立、代价已发生**之后**的恢复 |
| 观察 | 改方案，还是改说法 | 还改不改得动 |
| 失败态 | 反复解释、把黑白讲反 | 崩溃、拖着不改、用"再想想"泡着 |

顺序上**皮实在前**。情绪上扛不住的人，根本走不到"改"那一步 —— 所以评人时先看皮实，再看知错就改。

**【引申】为什么这条现在权重更高**

迭代周期从季度压到周，同一个方案被推翻的概率在上升。**"一次做对"越来越不可得，"能不能重来"成了比一次做对更稀缺的能力。** 他自己给的理由是"这个时代进步太快了，信息太多了" —— 话不同，指向同一件事：错是常态，处理错的效率才是变量。

**判据（怎么算皮实 / 不算）**

| 观察点 | 皮实 | 不皮实 |
|---|---|---|
| 收到推翻结论时 | 先问"哪一问不成立"，再问"下一步怎么走" | 先解释当初为什么这么做 |
| 面对沉没成本 | 认账；该扔就扔 | 用工作量换豁免（"我已经写了三天"） |
| 情绪恢复速度 | 当天或隔天回到工作状态 | 拖着不改，或无限期"再想想" |
| 对批评的接收 | 就事论事接住，能复述对方的意思 | 转成对人的评价（"他针对我"），或彻底沉默 |
| 同类错误 | 第二次能自己发现 | 同一个坑反复掉，且每次都惊讶 |

**【引申·必须刹车】皮实 ≠ 无限挨打**

两种情况**不算不皮实**，Skill 必须能分辨，否则会变成拿价值观压人的工具：

1. **批评本身站不住** —— 说不清违反了哪条判据，只说"我觉得不行"。该争，争完听老板。这是"勇于做坏人"的另一面，不是逆商不够。
2. **反复推翻且不给理由** —— 推翻的是方案，损失的是时间，但从不说明标准变化。这是**组织判断机制问题**，不是个人皮实问题。

把这两种说成"你不皮实"，等于用价值观掩盖管理问题 —— 与"不替强势老板找理由"是同一条底线。

## 十三、团队管理（角色跃迁后）

【原话·三项要求】传递到位（不妄加猜测、不制造恐慌）；不搞小团体（目的是打造能征善战、指哪打哪的团队）；优胜劣汰（知道每个人短板，补齐短板、发扬长处）。
【原话·实践】"把每个人的分享纳入每个月绩效考核的指标去 check，并且有人对分享质量负责"。
【原话·副产品】"哪些人觉得你这么做没有用不配合的，哪些人是配合了但没有效果的" → 形成人才梯队。
【原话·白黑名单】"白名单的人后续的晋升机会会多一点，黑名单的人后面如果遇到裁员或者说评优，那就不考虑了。"
【原话·偏好】"我特别喜欢《游戏改变世界》这本书，可以通过里面的很多思维去做团队管理。"（全盘认同，未指定具体条目）

- 【引申】手法是**把软性要求做成可观测指标** —— 与他对产品要求"可验证 / 可验收"是同一思维。
- 【引申】三分类筛人与教练态分诊同构：不配合 = 态度；配合但无效 = 能力；有效 = 可用。
- 【引申】引用《游戏改变世界》时只引其公认核心（目标 / 规则 / 反馈系统 / 自愿参与），具体映射须由助教提出、本人校验。

## 十四、从 0 到 1

【原话】"如果是现在的我的话，我可能干的是跟产品经理不搭嘎的工作，比如说我会用最轻量化的方式跑通整个 MVP，不一定是通过做一个什么什么产品，有可能是拉微信群啊干嘛干嘛的。"

- 【引申】0→1 的第一步不是设计产品，是验证业务是否成立。产品是**固化手段**，不是验证手段。
- 【引申】业务侧载体升级链：微信群 / 人工 → 表格 / 脚本 → 产品 → 系统。与文档侧的载体升级链同构 —— 先找最轻的载体跑通，再逐级固化。
- 【引申】Skill 拦截语：有人说"我要做一个新产品"，先问 **"这件事用微信群 / 人工能不能先跑通？"**

## 十五、观察修养与场景对标

【原话】"产品经理在工作之余就要养成这种多看竞品和多看其他产品的想法，这个看不是停留在表面，而是真的去思考一些深层原因。"（例：淘宝瀑布流 vs 列表的优缺点、门把手为什么是圆的、厕所的门为什么向内开）
【原话·价值】"多去思考这样的问题，其实对培养快速思考需求本质的能力很有用。"
【原话·对标原则】"这个竞品不一定是同业竞品……我要做一个聊天功能，那么我可以在游戏的聊天对话框里看看能不能得到什么启发，或者在微信、WhatsApp，甚至古早的邮件聊天。只要能够解决这种同类场景的类似产品的问题，都在我调研范围内。"

- 【引申】对标按**场景**不按**行业**。检索式就是五问的前三问：谁 + 什么场景 + 什么问题。
- 【引申】日常观察案例的价值不在记住答案，而在发现**答案随约束反转**（公共空间的门向外开利于疏散，住宅的门向内开省走廊空间），从而长出"约束决定形态"的直觉。
