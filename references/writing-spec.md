# 线框与规则说明：怎么写（CRM 场景）

> **这份文件的性质，先说清楚。**
> 他本人只做评审，不给写法（硬规则 15「不替设计师做设计」、硬规则 10「只报差距不给成品」）。
> 所以本文件的标记是：
> `【原话】` 他本人所述，可直接引用｜`【引申】` 从他的判据推导｜**`【通用】`** 行业通行做法，**不是他的话**。
> 本文除明确标 `【原话】` 的条文外，其余全部是 `【通用】`/`【引申】`。
> **产出用这份，验收用 `interaction-review.md`。** 两份是一对：这份管写，那份管查。

---

## 零、写之前先定三件事

1. **读者是谁**：开发（要建表建接口）／设计（要出视觉）／测试（要写用例）。同一张图给这三拨人看，需要的信息不同 —— 开发要字段和状态，设计要布局和层级，测试要边界和异常。
   【原话】"我写文档的目的是什么？是给谁看的？他看这个文档的目的是什么？"
2. **这份写到哪一级**：页面级（这一页有什么、点了去哪）／实体级（这个对象有几种状态、什么条件下能变）。
3. **一条规则归谁**：见第二节。**一个规则只在一个地方定义，其他地方只引用。** 这条定了，后面开发才不会拿着两处不一致的说明来问你。

【引申】载体选择按歧义度递减：文字 → 表格 → 图 → 参考链接 → 可交互原型。判据不是"规范要求"，是"这个读者靠它能不能复原我的意图"。【原话】"能用表说清就用表，能用图说清就用图。"

【原话·模块边界】"写文档的时候一定要有类似微服务架构的意识：我做这个模块，得知道模块边界在哪、和哪几个模块要联动、在什么地方要联动、联动的值是什么（哪些数据 / 元数据产生了联动）。"

—— 写文档前，除了定读者、定层级、定规则归属，还要写清**模块边界与联动**：这个模块管到哪为止，跟哪几个模块有数据往来、在哪个环节、传什么数据。写清了，开发才知道联调要找谁，需求突破边界时你也能第一时间知道找谁协同。

## 一、线框：框上必须能看出来的东西

线框分四级，不要跳级画 —— 上面一级没定，下面画了也要重画。

| 级 | 画什么 | 定完才能往下 |
|---|---|---|
| **L0 页面树** | 有哪些页面、怎么进去、层级关系 | 页面边界 |
| **L1 列表页** | 搜索/筛选/排序/分页/列/行操作 | 数据怎么被找到 |
| **L2 详情页** | 字段分组、状态表达、操作位置 | 一条记录怎么看、怎么动 |
| **L3 表单/弹窗** | 字段顺序、校验提示、按钮 | 数据怎么进来 |

### 1.1 L0：CRM 的页面树（示例）

```
线索池        待分配 / 我的线索 / 已转化 / 已废弃
客户          列表 → 详情（概览 / 联系人 / 商机 / 合同 / 跟进动态）
商机          看板视图 / 列表视图 → 详情（阶段推进 / 报价 / 赢单丢单）
合同          列表 → 详情 / 审批流
活动（跟进）   挂在客户与商机下，不单独成页
报表          漏斗 / 业绩 / 跟进量
```

【通用】页面树只画到"能一眼看出用户从哪进、到哪去"这一层，不要在这里画界面。**这一级他本人没谈过，属于补齐项。**

### 1.2 L1：列表页画框时必须出现的元素

【原话】列表页就查两件事 —— 易搜索、易定位。所以框上这些元素一个不能缺：

| 元素 | 框上要看出什么 |
|---|---|
| 搜索框 | 有无；**搜索字段写在图注里**（搜名称还是搜编号、搜不搜备注） |
| 筛选器 | 哪几个字段、单选还是多选、能不能和搜索叠加 |
| 排序 | 默认按什么、能不能改 |
| 分页 | 分页还是滚动加载、每页多少条 |
| 关键列 | **用户靠哪一列认人，那一列必须在首屏** |
| 行操作 | 高频操作直接露出，不进"更多" |
| 批量操作 | 勾选后才出现，还是常驻 |
| 空态 | 没有数据时说什么 |
| 无权限态 | 看不到的字段是隐藏还是显示"无权限" |

CRM 客户列表的"认人列"通常是：**客户名称 + 负责人 + 最近跟进时间**。【通用】其余十列该折叠就折叠 —— 列的信息密度错配是列表页最常见的深层错误。【原话】

### 1.2a 易定位的深化：先给字段排优先级，再上框

【原话】"列表页里面我们经常能看到很多字段，我们能不能知道哪些字段是用户搜索这一条数据时最核心考虑的字段？"

—— 定位的核心不是"有没有搜索框"，是**用户靠哪几个字段认这一条**。所以画框前先做一件事：**给字段排优先级**，把核心字段挑出来。

【原话】"这个排序场景可能会根据不同用户在不同场景下需要不同的字段……我们得去考虑哪一种情况的概率是最大的。"

—— 优先级不是固定的，随场景变。判据不是"哪个字段重要"，是**哪一种使用场景的概率最大**；概率最大的场景里，那个核心字段就是最高优先级。

【原话·落地】"我们要把这个字段优先级提前面，或者在视觉聚焦点上要更有一些聚焦点。"

—— 两个落点：① 字段在列里**往前放**；② 视觉上**做聚焦**（首屏可见 + 强调）。优先级高的字段，用户扫一眼就要能对上号。

### 1.2b 易搜索的深化一：查询与展示要咬合

【原话】"每一个列表页的信息都得被查询包含，或者说我查询能查的东西在列表页你得有。如果我查询的这个 key 在列表页没有对应的 key 的话，那相当于我查到了也不知道这条数据是不是。"

—— 一条硬约束：**可搜索字段 ⊆ 列表展示字段**。用某个 key 查，列表里得有同一个 key 能对上号，否则查到了也认不出、确认不了这条数据。设计时把「可搜索字段」和「列表展示字段」放一起对一遍，不能各定各的。

### 1.2c 易搜索的深化二：筛选项分层，不穷尽

【原话】"我们不能把所有的东西都作为筛选项……我们也得盘哪些筛选项是高频的，要把它放到前面，不高频的可以收起来、可以配置。"

【原话·场景取舍】"核心就看场景。C 端的产品我们就要做取舍了；B 端的产品可以灵活一点、配置一下。"

—— 筛选项按**使用频率分层**：高频的直接露出来、放前面；低频的收进"更多筛选"或做成可配置。C 端克制做减法（只留最高频），B 端可以放开，按角色 / 场景给不同筛选集。

### 1.3 L2：详情页先承接列表页，再填两个清单，再画框

#### 第 0 步：承接列表页，先让用户确认"没进错"

【原话】"详情页最核心要解决的一个问题，本质上是对列表页的承接，因为每一个详情页它本身都会有前置入口。"

【原话】"我们一开始要解决的问题，就是给用户一个感觉：你从这个地方进来的，你没进错。"

【原话】"列表页的一些关键信息到详情页，是需要有一定的承接的，或者说是直接展示出来的，让用户有一种感知——我进对了，没进错。"

—— 列表页上用户用来"认这条数据"的那几个关键字段（见 §1.2 字段优先级），到详情页要直接、醒目地承接住，放在最上面。用户一眼能对上号，才谈得上往下看。

#### 第 1 步：填两个清单

【原话】"然后我们才需要考虑用户想知道什么，和我们想让他知道什么，我们需要列出来。"

【原话】"在这个场景下，用户想要知道的信息是什么？我们想让用户知道的信息是什么？对应的操作按钮是不是在相关的场景附近。"

以 CRM 客户详情为例：

| 用户想知道 | 我们想让他知道 |
|---|---|
| 这个客户是谁、做什么的 | 客户等级 / 来源（影响他跟进的优先级） |
| 现在谁在跟、多久没联系了 | 归属规则：撞单了归谁 |
| 跑着几个商机、到哪一步了 | 跟进超期提醒 |
| 有没有合同在审批、卡在谁手上 | 商机在某阶段停留多少天算异常 |
| 有没有欠款 | 客户是否在黑名单 / 是否有风险标记 |

**差集就是这页面的设计重点。**【原话】CRM 里最常被两边同时漏掉的是**过程态**：商机卡在第几阶段多少天、合同现在在谁手上审 —— 这类"在途中"的信息，用户想知道、我们也该让他知道，但两边清单里都不写。

#### 第 2 步：分层级、分优先级、归类

【原话】"分层级、分优先级、然后归类：相同类的放相同区块，不同类的放不同区块。区块和区块之间有优先级，区块间的字段有优先级。"

—— 三个动作：① **归类**：同一类的信息放同一个区块，不同类的拆开；② **区块优先级**：区块与区块之间排先后（最重要的区块在最上）；③ **字段优先级**：区块内部字段之间也排先后。列表页是"字段一级排序"，详情页升级成"区块 + 字段两级排序"。

#### 第 3 步：按钮按 action 相关性分两路

【原话】"按钮要考虑它到底是在整个详情页都可能会操作到的使用场景，还是只有用户锚定到某个字段、某个区块的时候才可能遇到。"

【原话】"整个详情页都可能用到的，就置底漂浮、或用漂浮的方式解决，按钮始终可见；只有锚定到某个字段/区块才会用到的，就放到它相关的地方。一定要考虑按钮 action 的相关性。"

—— 两路分法：

- **全局动作**（全页都可能触发，如保存、提交、分享）→ 置底漂浮 / 悬浮，始终可见
- **局部动作**（只作用于某个字段或区块）→ 贴着它作用的对象放（就近原则）

按钮就近（【原话】"操作按钮是不是在相关的场景附近"）：

- 改负责人 → 贴着"负责人"字段，别放页面底部通栏
- 推进阶段 → 贴着阶段条
- 新建商机 → 放在商机区块的表头
- 通栏按钮只留给"整页级"动作（保存整张表单）

### 1.4 L3：表单的字段顺序

【通用】按**用户的判断顺序**排，不按表结构排。CRM 新建客户时，用户脑子里是"这是哪家公司 → 谁给我的 → 归谁跟"，所以顺序是：客户名称 → 来源 → 负责人 → 联系方式 → 其他。把"客户编码"放第一个，是给数据库排的，不是给人排的。

### 1.5 L3：表单校验 —— 规则、报错、层级

【原话】"详情页有静止态（展示态），也有编辑态、新增态。在编辑态和新增态里，很多人容易犯的一个错误，就是表单校验逻辑。"

【原话】"最考验人的其实是：我们得告知用户，他哪里出错了。"

#### 1.5.1 校验规则：先给全规则，再谈提示

【原话】"要给一个相对完善的规则：必填非必填、字段限制、长度限制、字段约束（类似正则的规则），还有字段和字段之间的联动校验，这些东西都需要列出来。"

—— 规则四件套：① 必填/非必填；② 长度限制；③ 格式约束（正则类）；④ 字段间联动校验。缺一个，测试就不知道该怎么验。

#### 1.5.2 报错提示：告诉他"正确的格式是什么"，且要短

【原话·例子】"用户注册页输密码，我们要求 8–16 位、大小写加数字，他来了个符号——我们不能只告诉他'你不符合格式'，得告诉他'你不符合格式，正确的格式是什么'。"

【原话】"提示要做到字尽可能短，让用户一眼看过去就能明白他该怎么做。"

—— 报错文案两条铁律：① **指路**：不只说"错"，说清"对的是什么"；② **短**：一眼看懂下一步。这条跟字段表的"报错文案照抄"是同一件事（见 §3 字段表）。

#### 1.5.3 校验层级：不同场景用不同交互

【原话】"提示有优先级：失焦校验、on change 校验、表单提交校验，输入框下方红字、表单提交弹窗——这些都是校验层级，必须根据不同场景判断用哪种交互形式合适。"

| 层级 | 用什么 | 适用场景 |
|---|---|---|
| **失焦校验** | 输入框下方红字 | 简单字段的必填、长度、格式（用户输完离开就验） |
| **on change 校验** | 联动渲染 / 即时判定 | 复杂控件、字段联动（如 A、B 改变后，决定其他字段的渲染和判定） |
| **提交校验** | 弹窗（可单可多重） | 交叉验证（字段之间互相制约的，提交时一起验） |

#### 1.5.4 提交校验的提示优先级

【原话】"提交这个地方一定要考虑提示的优先层级：比如有五个提示，先校验哪个、再校验哪个，得排出来。可能有多重弹窗去校验；如果做得细，可以放在一个弹窗里。"

—— 提交时多个错误一起冒，要：① **排优先级**：先报哪个、再报哪个（通常是阻断最狠的在前，或按用户最该先处理的在前）；② **收敛**：能一个弹窗装下的就别弹五下，一个弹窗里分层列清。

#### 1.5.5 边界：哪些不是产品方案要写的

【原话】"我不会专门在产品方案里说防重复提交的问题，这是个技术路线，不是产品方案要弄的。"

【原话】"部分成功、超时、并发冲突这些，我认为都不是现阶段产品经理需要去考虑的内容，它是整个方案底层的东西，需要系统架构师去考虑。"

—— 一条边界：**产品方案写"用户要什么、系统怎么反馈"，不写"底层怎么实现"**。防重复提交、部分成功、超时、并发冲突属于技术 / 架构层，是系统架构师的活。产品经理要懂（有技术 sense），但不写进方案。

## 二、三层规则：归属、定义、引用（这份文件的核心）

三类规则不是三种文体，是**三个归属层级**。搞不清归属，就会出现同一件事在三处各写一遍、三处还都不一样。

### 2.1 归属表

| 层 | 挂在哪 | 只回答一件事 | 换页面还成立吗 | 编号 |
|---|---|---|---|---|
| **业务规则 BR** | 实体 / 对象 | 状态怎么变、什么条件下允许、跨对象影响是什么 | 成立 | `BR-01` |
| **交互规则 IR** | 页面 + 动作 | 用户这一下点了之后，系统做什么、怎么反馈 | 不成立 | `IR-客户新建-03` |
| **字段规则 FR** | 单个字段 | 这个字段怎么填、怎么校验、什么时候不可改 | 只对这个字段成立 | `FR-客户.客户等级` |

### 2.2 归属三问（拿不准时问这三句）

1. **换个页面还成立吗？** 成立 → 业务规则；不成立 → 交互规则。
2. **换个字段还成立吗？** 成立 → 交互规则；只对这个字段成立 → 字段规则。
3. **说的是"能不能"还是"怎么提示"？** "能不能" → 业务/字段；"怎么提示" → 交互。

### 2.3 实例：CRM 撞单，一条规则拆成三条

这是分层最见效果的地方。同一件事，三层各写一段，互不重复：

> **BR-07（业务规则·客户实体）**
> 客户以「统一社会信用代码」唯一。新建时若已存在相同代码的客户，**不允许创建**，返回已存在客户的负责人与创建时间。
> 例外：已流失客户可被重新认领，认领后原客户的商机与合同不自动迁移。

> **IR-客户新建-03（交互规则·新建动作）**
> 提交时命中 BR-07：弹窗展示"该客户已存在，负责人：张三，创建于 2025-03"，提供「申请协作」与「取消」两个动作。
> **不提供「强制创建」**。点「申请协作」后通知原负责人，状态置为待确认。

> **FR-客户.统一社会信用代码（字段规则）**
> 必填（海外客户可为空，为空时不参与唯一性校验）／18 位／仅大写字母与数字／失焦校验格式／提交时校验唯一性／报错文案："该统一社会信用代码已被「{客户名称}」使用"。

三段的边界很清楚：**BR 说能不能，IR 说怎么提示，FR 说这个字段本身怎么填。** 后面谁要改，只改一段。

### 2.4 引用，不重抄

- IR 里需要业务条件时写：`依赖 BR-07`，不把 BR-07 的文字抄一遍
- FR 里需要跨字段逻辑时写：`见 IR-客户新建-04`，不在这里重写
- **一条规则出现两遍，就是后面必对不上的源头。**自检时专门查这一条。

### 2.5 跨字段/跨对象规则写在哪

这是最容易漏的一类（"电话和邮箱至少填一个"、"合同金额不能超过商机金额"）：

- **同一表单内的跨字段校验** → 交互规则（`IR-客户新建-04`），字段表里两列各注一句"见 IR-客户新建-04"
- **跨对象的约束**（合同金额 vs 商机金额）→ 业务规则（`BR-xx`），因为它换个页面还成立
- **自动回写/计算字段**（最近跟进时间由活动触发）→ 业务规则写触发条件，字段表写"只读，由 Activity 回写"

## 三、字段表：列头定死

【通用】固定 13 列。多了没人填，少了必漏。

| 列 | 写什么 | 不合格长什么样 |
|---|---|---|
| 字段名 | 用户看到的名称 | 用数据库字段名当字段名 |
| 字段编码 | 英文/下划线 | 缺 —— 开发只能自己猜 |
| 类型 | 文本/数值/日期/枚举/关联/附件 | 只写"字符串" |
| 长度精度 | 字符数、小数位 | 缺 —— 开发按默认值建，后面改表 |
| 必填 | 是/否/条件必填（写条件） | 写"视情况" |
| 默认值 | 具体值或"当前用户""创建日+3天" | 缺 |
| 取值范围/枚举 | 枚举**写全**，且分「存值 / 展示值」 | 只写"下拉选择" |
| 可编辑条件 | 什么状态下谁可改 | 写"可编辑" |
| 校验时机 | 失焦 / 实时 / 提交 / 无 | 缺 |
| 报错文案 | **照抄原句** | 写"给友好提示" —— 测试没法验 |
| 是否可搜索 | 是/否 | 缺 —— 列表页画不出来 |
| 是否列表展示 | 是/否 | 缺 —— 同上 |
| 备注 | 关联的 BR/IR 编号 | 空着 |

**两条硬要求：**

1. **枚举必须写「存值 / 展示值」。** CRM 的客户等级存 `1/2/3`，展示"重点/普通/潜在" —— 不写清，开发按展示值存，后面报表全错。
2. **报错文案照抄。** "请填写正确的统一社会信用代码" 和 "该统一社会信用代码已被「XX公司」使用"，测试验的是两句不同的东西。

## 四、图和规则怎么挂：标号法

【原话】对账要求"图里有的元素，文字里有没有约束"。但**读法**给了（去图的右侧或下方就近找），**写法**没给。【通用】补齐如下：

1. **图上标号**：控件左上角标 ①②③，编号与 IR 编号一一对应（①= `IR-客户列表-01`）
2. **图注只写一句**：这个控件是什么 + 编号。规则正文不写进图注
3. **规则正文集中在图后面**，按编号顺序排，一条一段
4. **一条规则只对一张图。** 一段说明被两张图共用 → 这就是对账不过（见 `interaction-review.md` 第零节 `caption_shared`）
5. **一组状态画一张图**（正常/空/错/加载/无权限放在同一张里分格），不要每个状态一张截图 —— 那样必然缺态
6. **交互说不清时的两个替代**（【原话】）：
   - "请参照什么 App 或者什么网站的什么功能，给一个链接"
   - "直接用 AI 生成一个 JS，你直接用这个 JS 就可以了"

**图上标号的收益**：评审时不用再靠"就近找"去猜哪段文字属于哪张图，直接对号；开发拿着编号能反查，不会漏读。

## 五、写完自检（只列阻断级）

按「会不会导致错误操作」过，阻断级不过不许往下走：

- [ ] 每个字段四件事齐了没：**必填、默认值、禁用条件、校验时机**（【原话】通用四查项）
- [ ] 每个按钮四件事齐了没：作用对象、作用范围（整页还是这块）、点完去哪、不可用时什么表现
- [ ] 每个页面四种状态齐了没：空态、加载、报错、无权限
- [ ] 跨字段/跨对象规则有没有**单独成条 + 编号**（不能只藏在字段表的备注里）
- [ ] 有没有一条规则在两处各写一遍
- [ ] 自动回写/计算字段：谁触发、什么时候、写错了怎么修
- [ ] 删除/作废：历史数据怎么办、能不能撤销、撤销后副作用谁清
- [ ] 状态能不能回退、回退后已产生的副作用谁清理（【原话】资金模块冻结态的教训）
- [ ] 枚举有没有写「存值/展示值」
- [ ] 报错文案是不是照抄原句，不是"友好提示"

## 六、评审：识别「写得不行」，只改文字不改样式

> 这一节给 skill 一个评审能力（借鉴 `system-to-prd`，全【通用】，不是张老师原话）：**先识别 PRD 哪里写得不行，再帮它改——但只改文字表达，不改样式 / 视觉 / 工程**（改样式太重，不值当）。

> 「写得不行」最常见的就两类：**图文没对照**、**话太啰嗦**。两类各藏几个子症状，对应几种"能简单改掉"的文字改法。识别症状 → 给改法，就是这一节干的事。

**总原则：表达越简单越好。** 尤其逻辑侧、字段侧的表达，宁可**不成句**，也用排版（换行 + 冒号 + 逗号）把「实体 → 项」的映射排出来，一眼看懂。**用最少的字数承载全量的信息。**

成句啰嗦版：

> 这个字段有四个状态，状态一的时候能干嘛，状态二的时候能干嘛，状态三的时候能干嘛，状态四的时候能干嘛。

映射列表式（不成句，但一眼看懂）：

```markdown
该字段共 4 个状态：
- 状态一：行动一、行动二
- 状态二：行动一、行动二
- 状态三：行动一、行动二
- 状态四：行动一、行动二
```

适用：状态 → 动作、字段 → 取值、条件 → 结果、角色 → 权限 这类"一对多映射"。

### 6.1 图文没对照 → 标号挂钩

- **识别**：线框图定位不到对应文字说明——图里有的元素文字没写约束，文字说的元素图里没有。
- **改法**：图上标号，文字按编号排（详见 §四「标号法」）。只改图注和文字编号，不动视觉样式。

### 6.2 话太啰嗦 → 一句一件事

- **识别**：50 字一段不换行、一段塞多件事、有编号却挤在一行、一段出现两个以上分号。
- **改法**（四条，照抄例子）：

  1. **并列拆列表**：谓语提到冒号前，列表每条只写不同部分。

     ```markdown
     **本页不支持：**
     1. 批量修改状态
     2. 重新提交
     3. 终止
     ```

  2. **改后能数出两条就分条**：4 件事挤一段 = 没写。

     ```markdown
     **改后：**
     1. 账户块从只读 9 项扩成两段
     2. 前段固定 9 项，按原顺序
     3. 后段"其他收款信息"，一行一个往下平铺
     ```

  3. **有编号就必须换行**：`1. 筛出待处理；2. 导出明细` 挤一行 = 没编号，读者看不出边界。
  4. **一段只讲一件事**：一段出现两个以上分号，切开。

### 6.3 篇幅失控 → 篇幅上限

- **识别**：某段远超合理长度。
- **改法**：按上限砍，超了怎么办——

  | 段 | 上限 | 超了怎么办 |
  |---|---|---|
  | 定位 | 3 段 | 砍掉功能罗列 |
  | 背景 / 场景 | 5 个场景 | 合并同类场景 |
  | 主流程 | 6 步 | 拆成"主流程 + 分支流程" |
  | 字段字典 | 1 表 15 行 | 拆成"基础项 / 条件项"两表 |
  | 业务规则 | 15 条 | 按子话题分组 |
  | 状态流转 | 10 个迁移 | 状态机拆成两个实体 |
  | 异常边界 | 10 行 | 只留会导致数据错误的 |
  | 待确认 | 8 条 | 说明前置闸门没过扎实 |

### 6.4 技术词塞正文 → 说人话 + 下沉附录

- **识别**：接口名、字段名、枚举名、表名出现在正文里。
- **改法**：换成"它保证了什么"，技术标识收进附录对照表。

  **技术词 → 人话对照**（照抄）：

  | 技术词 | 换成 |
  |---|---|
  | 落库 / 入库 | 存下来、记为 |
  | 幂等 | 重复点也只生效一次 |
  | 序列化快照 | 把当时那张单原样复印一份存起来 |
  | 接口返回 / 回执 | 银行回话；回话了才算数 |
  | 轮询 / 定时拉取 | 系统每隔 X 分钟去问一次 |
  | 回调 | 对方主动把结果推回来 |
  | 校验 / 前置校验 | 提交前先检查 |
  | 并发 | 两个人同时操作 |
  | 事务 | 一起成功或一起失败 |
  | 灰度 / 开关 | 先对一部分人开 |
  | 超时 | 等到规定时间还没回话 |

  **附录对照表**（三列：正文说法 ↔ 界面位置 ↔ 实际对应）：

  | 正文说法 | 界面位置 | 实际对应 |
  |---|---|---|
  | 打款方式 | 列表第 3 列 | `paymentMethod` |
  | 支付协议 | 明细「打款信息」块 | `paymentScheme` + `local_clearing_system` |
  | 「确认出款」 | 抽屉底部主按钮 | `POST /finance/payout/payout` |

  判据一句话：这句话删掉后，业务方还需要知道什么才能做决定？需要 → 用业务语言留在正文。

### 6.5 规则说不清 → 配 case + 真值表

- **识别**：带条件的规则没有例子；字段的「显示 / 必填 / 可编辑」由两个以上条件控制却散着写。
- **改法**：
  - 规则配 **case**（五要素、≤5 行）：谁（具体人）→ 做什么（具体值）→ 系统怎么反应 → 看的人据此做什么。别用"例如某客户"、别只写 happy path、别写成测试用例。
  - 多条件控制用**真值表**一行一格覆盖全组合，行数 = 组合数，不许"其余类似"收尾；前后端两套判断分开列。

### 6.6 迭代改动没讲清「改前 / 改后」 → 对比式写法

- **识别**：迭代方案里，读者看不出"改前什么样、改后什么样"。
- **改法**：用对比式文字写清三段——**what**（改成了什么，可核查）+ **why**（为什么改）+ **impact**（下游影响：哪些字段 / 页面 / 模块跟着变）。

  例：`what=新增"客户等级"字段｜why=销售要按等级排跟进优先级｜impact=列表页、详情页、字段表三处同步`
